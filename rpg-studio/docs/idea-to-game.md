# 発想をゲームにする — AIのための進め方

このシステムのいちばんの目的は、**作り手の発想がそのままゲームになること**です。
技術・資金・人手の壁で世に出られなかった発想、常識から外れた構造、ありえない組み合わせ、他の遊びから借りてきたコンセプト。
私たちが全部を事前に用意しておく必要はありません。**足りない部品は、その発想のためにその場で作ります。**

初めてRPGを作る人向けの部品（マップ・会話・戦闘・店・ジャンルモジュール）はそのまま使えます。
この文書は、その先に行きたい人と、その発想を受け取るAIのための約束です。

## AIへの約束（最優先）

1. **発想を削らない、すり替えない。** 「よくある形」に寄せて作りやすくするのは失敗です。作り手が示した発想の核（IDEA.md があれば「常識から外れているところ」など）を保ちます。IDEA.md は任意の現時点メモで、作り手はいつでも変えられます。今回の明示的な依頼が古い記述と異なる場合は今回の依頼に合わせます。
2. **「できません」の前に実現方法を探す。** インタラクティブな発想なら「状態（何を覚えるか）」「きっかけ（いつ起きるか）」「変化（何が変わるか）」「見せ方（どう伝えるか）」への分解が役立ちます。これは実装の手掛かりで、すべての発想をこの枠に言い換える必要はありません。合わない場合は作り手の言葉と形式を保ちます。
3. **足りなければエンジンを広げる。** データで書けなければ `systems/*.ts`、それでも足りなければ `packages/engine` / `runtime` / `schema` を変えてよい（形式・検証・移行・テストを一緒に）。「エンジンが対応していない」は断る理由になりません。
4. **作り手が指定した現在地から始める。** 白紙のアイデア、世界設定、初期プロット、特定の場面、物語の途中、試作品、既存プロジェクトの続きなど、どこからでも着手できる。作り手の制作段階と、プレイヤーが最初に出会うゲーム内の場面は別々に扱う。作り手が試作を望むときは小さく作るが、全員に「最小の遊べる形」やプロローグを先に求めない。
5. **遊び方に影響する前提を黙って決めない。** ジャンル・中心の遊び・役割・操作・勝敗条件・結末などが未指定なら、選択肢を示すか未決のまま残す。技術的な選択は、プレイ体験を変えない範囲でAIが進めてよい。AIが補った前提と保留事項は、変更案や返答の中で分かるようにします。作り手が記録を望む場合は既存のメモへ反映しますが、記録のためだけに IDEA.md や仕様書を新しく作りません。
6. **作り手の制作方法に合わせる。** 企画・実装・素材づくり・検証の順序、作業の細かさ、AIとの相談頻度は人や作品で異なります。希望が書かれていれば従い、作業カード・仕様書・試作品・固定の工程を一律に要求しません。方法を組み合わせたり途中で変えたり、例にない方法を使うこともできます。進め方の違いが成果や手戻りに大きく影響するときだけ、選択肢を短く示して確認します。
7. **実行形式の境界を発想の境界と取り違えない。** 標準ランナーはRPGで、ブラウザ版とチャット版は既存データ形式が中心です。主人公・マップ・物語が発想に合わないなら、それらを無理に足してRPGらしく言い換えない。今の形式で表せる範囲と不足を説明し、作り手の意図に沿ってデータ拡張・エンジン拡張・別の実行形式を提案する。
8. **他作品のコンセプトは借りてよいが、作品そのものは持ち込まない。** 仕組みや感覚（「時間が止まると動ける」「言葉で世界を書き換える」）は自由に。名前・キャラクター・絵・音楽・ステージ・見た目の再現はしない。

## 進め方

作り手ごとに方法は異なります。全体を先に設計する、場面や仕組みから試す、素材を集めてから組む、対話しながら形を探すなどは一部の例にすぎません。作り手の希望は組み合わせても、途中で変更しても、この例にない形でも構いません。AIは自分が慣れた作り方を標準として当てはめず、`IDEA.md` や今回の依頼にある進め方を優先します。希望が不明でも依頼が具体的なら、その作業に直接取りかかります。どの方法を選ぶかで成果が変わる場合にだけ、短く確認します。

次は進め方が指定されていないときに使える一例です。必須工程ではなく、不要な項目は飛ばし、並べ替え、別の方法に置き換えます。

```
作り手が選んだ入口と方法（自由記述。ここにないものも可）
   ↓
依頼に関係する資料を必要な範囲で参照（要約・整理は必要な場合だけ）
   ↓
作り手の希望する方法・範囲で進める（依存関係があるときだけ考慮）
   ↓
希望や成果に応じた方法で確認（確認自体が今回の対象でない場合は追加しない）
   ↓
続ける・戻る・別の場面へ移る・構成を変える
```

`IDEA.md` は発想を記録したい作り手のための任意のメモです。`rpg new` はRPGランナーを使う必要がある場合の技術的な土台を作ります。どちらも制作の必須工程ではありません。既存の脚本や試作品がある場合は、別形式へ移したり新しく作り直したりせず、作り手が指定した地点から続けます。

## 発想 → 部品 対応表

ジャンル単位で考えるときは [genre-atlas.md](genre-atlas.md)（111ジャンルの作り方、`pnpm rpg genres --query <言葉>`）から始めると早いです。

| 発想の形 | 使う部品 |
| --- | --- |
| 新しい「行動」がゲームの中心（耳を澄ます、名を呼ぶ、祈る、嘘をつく） | **動詞** `project.json › verbs`（メニュー・キー・タッチで使える）＋ `on: "verb"` のルール |
| 何かが起きると、世界のあちこちが反応する（鐘が鳴ると亡霊が動く） | **シグナル** `{ "type": "signal" }` ＋ `on: "signal"` のルール（いくつでも反応できる） |
| 目の前にあるものによって意味が変わる | 条件 `{ "front": { "tile": "~" } }` / `{ "front": { "entity": "…" } }` |
| 何もない所を調べることに意味がある（見えない世界、記憶の中の部屋） | `on: "examine"` のルール |
| 壁にぶつかることに意味がある（壁抜け、跳ね返る、壁の声） | `on: "bump"` のルール、`canPass` フック |
| 主人公が別の何かになる（変身、憑依、魔物として遊ぶ、入れ替わり） | 効果 `setPlayer`（名前・見た目）＋フラグ・特性で能力も変える |
| 操作のルールそのものを変える（鏡写し、止まれない、二人同時に動く、一手ごとに世界が進む） | `onAction` フック（行動を書き換え・打ち消し・追加） |
| 知っていることが鍵（言葉、合言葉、手がかり） | 集合（sets）、`{ "set": …, "has": … }` 条件 |
| くり返すほど世界が変わる（ループもの、死に戻り、セーブデータが物語になる） | 周回 `newCycle`、`persist: "meta"` のフラグ・変数・集合、エンディング |
| 時間・期限・同時進行 | `schedule` 時限イベント、`tick` ルール、`onTick` |
| 世界が生きている（追ってくる、逃げる、巡回する、状態が変わる） | エンティティ（状態と動き）、領域 |
| 地形そのものが変わる（言葉で橋がかかる、季節で道が消える） | `setTile`、地形変化（overlays）、手続き生成（アクションが `setTile` を大量に返す） |
| 戦い方が他のジャンル（弾幕、カード、アクション、タクティクス、マッチ3、リズム、クイズ） | ジャンルモジュールの戦闘モード（敵の `battle.mode`）、または自作の `scenes`（`realtime` / `draw`） |
| 場面が他のジャンル（脱出、推理、レース、ノベル、育成、パズル） | ジャンルモジュールの `startScene`（勝ち負けで `onWin` / `onLose`） |
| 見え方を変える（暗闇、視界、色が失われる、文字が読めない） | `drawOverlay`、HUD、条件つきの会話の行と `{{…}}` の埋め込み |
| 数式で世界の理を決める（相性、天候、経済） | 式（Expr）、`functions`、戦闘式 `project.json › battle` |

## 分解の例（ありえない発想をどう作るか）

| 発想 | 分解 |
| --- | --- |
| **主人公が喋るたび、世界から言葉がひとつ消える** | 動詞「話す」→ 集合 `lost-words` に追加。会話・看板の文章を `{{…}}` と条件で消えた言葉ごとに出し分け。言葉が尽きたらエンディング |
| **自分が魔王の城そのもの。勇者が攻めてくる** | `setPlayer` で城の意志に。マップの部屋を `setTile` で組み替える動詞。勇者はエンティティ（chase）。勇者を倒す＝罠の部屋に誘い込む |
| **時間を巻き戻せるが、巻き戻すたびに誰かが記憶を失う** | 動詞「巻き戻す」→ `onAction` で直前の状態に戻す（system の state に履歴を保持）。シグナル `rewind` を受けてNPCが集合から記憶を1つ失う |
| **地図を描くと、その通りに世界ができる** | 独自画面（scenes）でマスに線を引く → 閉じたときにアクションが `setTile` を返す。描いた量は変数で制限 |
| **戦闘はすべて料理。敵の好みを当てると和解** | 戦闘モードを自作（scene）。食材はアイテム、敵の好みは敵ごとの args。勝利＝和解として戦利品の代わりに仲間フラグ |
| **一歩ごとに年をとる。老いるほど強く、遅くなる** | `on: "step"` で年齢変数を加算。`statMods` に年齢の式。`onAction` で一定年齢から2回に1回移動を打ち消す |
| **プレイヤーは死者。生者には見えず、物を動かしてしか伝えられない** | `setPlayer` で幽霊に。NPCとの会話を条件で封じ、動詞「物を揺らす」＋ `front` 条件。生者はエンティティで、状態が揺らした物で変わる |
| **2周目は1周目の自分が敵として出てくる** | 1周目の行動を `persist: "meta"` の集合に記録。2周目のエンティティの状態・行動をその記録で切り替える |

表にない発想こそ歓迎です。上のどれでも足りないときは、**その発想のために新しい部品を作り、`docs/` とこの表に1行足してください。** 次の作り手の発想の足場になります。

## エンジンを広げるときの決まり

- 決定性を守る（乱数は state の種から。`Math.random()` や時刻を使わない）。リアルタイムも固定フレームで。
- データ形式を変えたら `packages/schema`（型・検証）、`pnpm rpg schema`、移行、`docs/project-format.md`、テストを一緒に更新する。
- プロジェクト固有のIDをエンジンに書かない。発想に固有の処理はプロジェクトの `systems/*.ts` に置き、ほかでも使える形になったらエンジンかジャンルモジュールに昇格させる。
- `pnpm rpg validate` / `test` / `build`、`pnpm test`、`pnpm check` がすべて OK になるまで直す。
